# Probing fifteen sourced candidates: five hits, nine silences

Run on 2026-09-03 at 13:02 MST, with the vehicle parked and awake immediately
after a highway drive, adapter reading 13.9 V. The drive session was pulled to
a workstation before the recorder was stopped, so nothing recorded was at risk.

Both profiles ran under the supervised `--confirm` path against exact
enumerated identifiers. No sweep, no guessed identifier, no service other
than `22`.

## Module `CB`, battery system manager: five for five

Source: meatpiHQ/wican-fw issue #884, a 2027 Bolt on the same Ultium/BEV3
extended-addressing scheme. Unmerged, single-author, not BT1.

Every one answered.

| identifier | source's description | payload | as integer |
|---|---|---|---|
| `27BF` | charge-cycle regeneration | `00 00 21` | 33 |
| `27BB` | thermal-management energy | `00 00 64` | 100 |
| `27B5` | thermal-management distance | `00 00 15` | 21 |
| `2709` | A/C compressor temperature | `6E` | 110 |
| `2AF1` | battery module temperature | **24 bytes** | see below |

That the addressing worked was never in question — this module already answers
eight other identifiers. What is new is that five more sourced-but-unproven
candidates all returned positive responses on the first attempt.

### `0x2AF1` returns twenty-four values

```
72 73 72 72 72 72 72 72 72 72 73 73 73 73 72 72 72 72 72 72 72 72 73 72
```

Twenty-four. That is the same count as the twenty-four module-like values in
`0x2B43` (26 = 2 + 12 + 12), and it is what a per-module reading should look
like on a pack whose series count measures 96 and whose array splits into two
blocks of twelve.

The values are tightly clustered — only two distinct bytes, 114 and 115 — which
is what a thermally healthy pack should look like sitting in one place.

**On the scaling, the honest position is unproven.** The source calls this
battery module temperature. Under `(x − 40) / 2` the twenty-four land at
**37.0–37.5 °C**, against a pack temperature of **39.0 °C** measured
independently by `0x0046` in the same minute. That is close — within 1.5–2.0 °C
— and close is not proof:

* it is **one sample at one temperature**. A scaling that happens to land near
  the right answer at 39 °C says nothing about whether it holds at 5 °C or
  55 °C, and a wrong offset is invisible when you only ever look at one point.
* `0x0046` may report a maximum, a different sensor, or coolant rather than a
  module mean, so a 2 °C gap is not necessarily error at all.
* the alternative `x − 40` gives 74–75 °C, which is not obviously wrong for a
  pack that had just been driven hard, only less likely.

The bytes are worth capturing now and decoding when a temperature *range*
exists to fit against. That is the same discipline that kept `0x5401` raw until
a charging session settled it, and the same discipline that produced a refuted
hypothesis rather than a wrong column earlier the same day.

## Module `40`, body control: nine silences

Source: OBDb/Cadillac-LYRIQ PR #14, which ships real-vehicle test vectors and
is the same pull request that supplied `2414` — an identifier this vehicle does
answer. That was the entire reason to take its other register families
seriously.

| identifier | source's description | result |
|---|---|---|
| `4149` | EVSE advertised current | `NO DATA` |
| `416C` | battery group voltage 1 | `NO DATA` |
| `416D` | battery group voltage 2 | `NO DATA` |
| `416E` | battery group voltage 3 | `NO DATA` |
| `434F` | HV battery temperature | `NO DATA` |
| `4127` | battery temperature A | `NO DATA` |
| `4124` | battery temperature B | `NO DATA` |
| `40E5` | battery coolant temperature 1 | `NO DATA` |
| `40E6` | battery coolant temperature 2 | `NO DATA` |

All nine. And the distinction matters: `NO DATA` is **not** a negative
response. A `7F 22 31` would mean "this module is here, understands
ReadDataByIdentifier, and does not have that identifier" — useful, and the
result these were expected to produce at worst. `NO DATA` means **nothing
answered at all**.

So this is not evidence that the LYRIQ's identifiers are wrong. It is evidence
that **nothing responded at `14DA40F1` on this vehicle**, which is a different
and more basic finding: either the body controller does not serve `22` at that
address, or it is not reachable through the gateway the way the battery manager
and brake controller are.

The vehicle names `40` as `BCM-BodyControl` in its own service 09 module
inventory, so the module exists. It simply did not speak. Whether a different
addressing reaches it is an open question this run does not answer, and the
adapter itself was fine throughout — it returned `13.9 V` to `ATRV` before and
after.

## What this changes

The immediate practical result is that the battery system manager has more to
say than was being asked of it, including a twenty-four-value array that lines
up with a pack structure derived independently from voltage ratios.

The immediate practical *non*-result is that the body controller, the largest
unexplored module on this vehicle and the one carrying the most interesting
candidate list, is silent to this approach. Recording that is worth as much as
the hits: it stops the next person spending a session rediscovering it.
