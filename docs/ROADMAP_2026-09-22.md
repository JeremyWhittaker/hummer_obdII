# Forward plan: turn Hummer discoveries into dependable telemetry

Prepared 2026-09-22 from the owner's original prompts and the
[independent review](PEER_REVIEW_2026-09-22.md). **Plan only: no implementation
or vehicle operation is authorized by this document.**

## The outcome we are pursuing

A dependable, read-only Hummer EV instrument that exposes useful measurements
ordinary OBD apps miss: motor RPM/torque and drive-unit temperatures, richer
battery/module detail, and doors/locks/lighting/HVAC. It should recover from
ordinary link failures, tell us why data is unavailable, load promptly on a
phone, and avoid repeatedly asking the owner to run service commands.

Success is a validated signal an owner can use, not a positive-response count,
a plausible scaling, or a colourful model. The existing exact allowlist,
separate scan gate, parked proof, DTC checks, serial pacing, default-session
only rule, private evidence and no-write/control/security prohibitions remain.

That is 7,424 module/DID reads: about **1.42% of eight full 65,536-DID
spaces**, ignoring alternate priorities and operating states. The 912 positives
are module/DID observations, may include previously known identifiers, and
must not be advertised as 912 new decoded signals. This batch promotes zero
new scanned signals into the production recorder. Scan counts await a private
raw-log audit; no local scan transcript was available for this review.

## Ordered work packages

### 1. Close reliability and truthfulness gaps first

Addresses review R1–R7 and the older browser blockers.

- Give recorder handover, scanner and watchdog a shared maintenance/ownership
  protocol. No watchdog restart or rebind during a held diagnostic operation;
  recover abandoned leases safely. Keep the narrow recorder start/stop
  permission rather than granting generic root commands.
- Remove the scanner's silent input-buffer-clear window without loosening
  reply validation. Preserve late and partial bytes even when the run aborts.
- Separate reload cooldown from cheap recovery; persist recorder-restoration
  intent until verified or explicitly cancelled. Make unknown health a
  distinct state and bound the age of actual failure evidence.
- Separate live rendering from explicit replay. Fix missing charging-state
  replay crashes, stale raw-array fallback and raw thermal-tint parsing.
- Correct the unattended recommendation and contradictory research claims.
  Bring the watchdog unit/timer definition into a reproducible, reviewed
  provisioning path after checking the actual installed configuration.

**Acceptance:** full suite plus failing-then-passing regressions for byte-arrival
races, watchdog/scan interleavings, partial recovery failures, unknown health,
and actual browser fresh → stale → recovered transitions. Simulated failed
operations leave both desired recorder state and evidence understandable.
No vehicle is needed to implement or validate these cases.

### 2. Build the evidence-to-signal analysis path

This is the main missing feature, ahead of another large sweep.

- Add read-only ingestion of scan/watch JSONL to the offline analysis tooling.
  Preserve module, priority, DID, session, UTC/monotonic timestamps, payload
  size and bytes, NRC, guard context, source-file hash and record identity.
  Verify raw hex/base64 agreement, incomplete transactions and torn records.
- Produce a module-qualified discovery catalogue: known baseline reads, new
  hits, negative/locked/conditional replies, tried ranges, aborted gaps,
  observations, candidate meanings, and validation status. Do not overwrite
  one ECU's meaning with another ECU's identical DID number.
- Record deliberate experiment events with timestamps and observer labels.
  Pair only genuinely overlapping candidate and reference measurements;
  report sampling skew, gaps and clock quality. A reference-only old drive
  cannot validate a candidate that was never sampled on it.
- Support bit changes, byte windows, signedness/endianness, constant fields,
  array structure, dynamic range and held-out experiments. Rank hypotheses;
  do not let unconstrained offset fitting manufacture “pack voltage.”
- Generate private coverage/guard summaries automatically. Public output must
  be a separately redacted export, never raw frames, VINs or connection details.

**Acceptance:** synthetic unknown DIDs survive ingestion byte-for-byte;
different modules never merge; torn/misattributed replies remain visible;
alignment rejects non-overlap; known existing signals are recovered as positive
controls; negatives and shuffled controls do not become confident decodes.
Then audit the actual scan artifacts in place on the node, read-only, in a
separately scoped continuation. Pin algorithm/configuration versions.

### 3. Deliver the first new body signals

Start with module `40 / 18`: door candidates `423D/423E`, fan/climate candidates
`41A9/41B5`; keep `4120/41AC` exploratory. These are leads, not promised outputs.

Design short attended parked experiments with a small named candidate set:
baseline → one manual change → return to baseline, repeated in a fresh session.
Record the event times. Separate driver door from other doors, locks, interior
lighting and vehicle wake; separate fan speed from A/C, heat and general
electrical load. Do not issue actuator commands or ask for unsafe states.

**Acceptance per signal:** repeated discriminating behavior, documented payload
bits/encoding and ambiguous states, independent observable reference,
negative controls, and clean guard evidence. Only then add the exact allowed
DID, module-specific decoder, raw retention, confidence entry, tests, catalogue
and a dashboard widget. If results are ambiguous, retain the lead without
promotion. A door-state widget is a more useful early win than four guessed
thermal units.

### 4. Pursue battery detail using the evidence already captured

- Audit CB array captures against known summary values from comparable times.
  Test partitioned/packed/header-bearing hypotheses, not only flat one-/two-byte
  arrays. Validate across more than one SoC and thermal state.
- Do not equate 96 effective series groups with total physical cell count, or
  an array index with a module's physical position. Those are separate claims.
- Study inverter/stator thermal candidates during normal parked thermal
  changes when permitted; temperatures do not require wheel motion to exist.
- After the importer and guarded operation are dependable, choose small
  supervised `CD` ranges, untried CB bands and omitted drive-unit bands based
  on evidence yield. Include `45` in the coverage ledger rather than silently
  treating it as scanned. Keep priority-specific results distinct.

**Acceptance:** an array/scalar relationship holds on independent observations
within justified measurement/timing tolerances; the proposed units and field
layout survive negative tests. Failure to match means “not decoded,” not
proof the signal is inaccessible. Expand discovery only with an explicit
range, expected duration and stop condition. Do not default to a 350-hour sweep.

### 5. Resolve the moving-validation dependency explicitly

Motor RPM and physical torque cannot be established from a static zero-speed
inventory. Keep the existing `2429` display in counts; do not invent Nm or
substitute wheel-speed animation for measured motor RPM.

First rank a very small named candidate set offline. Then draft a separate
supervised moving-validation protocol for owner approval: exact modules/DIDs,
fixed low request budget, duration, independent wheel-speed/current references,
DTC handling, abort rules and a passenger/operator arrangement that does not
distract the driver. It must have its own reviewed experimental admission;
**do not remove the scanner's zero-speed check or pre-promote unknown DIDs
into the normal recorder to make the experiment possible.**

**Acceptance:** explicit protocol approval, offline refusal/bounds tests, then
repeatable measurements over adequate range on independent sessions. A speed
ratio alone does not establish shaft location, and correlation alone does not
establish torque units. Session control, security access and actuation remain
out of scope even if an identifier requests them.

### 6. Make the daily dashboard fast and immediately useful

Can proceed alongside offline analysis after the R3 correctness fix.

- Give the owner a concise current-state page: energy/SoC, voltage/current,
  speed, thermal summaries, DTC status, validated body signals, age and
  confidence. Keep unknowns distinct from zero.
- Separate lightweight current-state polling from versioned/cached replay
  history. Avoid sending a whole 600-row window on every five-second update
  when the selected historical session has not changed.
- Add a diagnostic status panel that distinguishes API/Pi reachability,
  recorder state, last sample, adapter/link health when available, and an
  explicitly established vehicle state. “No fresh telemetry” is not proof of
  either sleep or complete OBD failure.
- Make explanatory prose expandable; keep model topology caveats and
  confidence accessible. Do not present distribution colours as fault alarms.
- Support telemetry replay without GPS, and keep location exposure opt-in.

**Acceptance:** desktop and phone Chromium/WebKit where available, actual
render/poll/replay tests including missing values, cold/warm loading metrics
on the Pi and owner's access path, payload/RSS/CPU budgets, and verified
freshness after a reconnect. Set numerical performance targets after measuring
that baseline; a desktop test time is not a Pi guarantee.

### 7. Verify deployment and operate without repeated manual chores

After approved implementation, use the existing narrow deployment paths;
verify deployed hashes, unit versions, port ownership and fresh samples.
Restore only the recorder state appropriate to the completed operation.
Exercise ordinary wake/sleep and disconnect/reconnect behavior before calling
it unattended-reliable. Continue the outstanding 12 V/sleep-power validation
from SAFETY.md; a software test suite cannot establish it.

For a future live scan, establish current supervision/readiness and a suitable
power window. Do not assume last week's parked state or charging waiver is
current. Routine approved recorder control should use the installed narrow
permission; if new privilege is truly needed, provide one exact owner command
and continue the independent offline work. No broad sudo grant is proposed.
